Build Plan

Otherworld Reads — Phases & Deliverables

Eleven phases, each one shippable on its own. The refactor comes first so everything after it is cheap; every feature phase after that adds a layer that can fail without taking the app down with it. Phase 7 is the point where it's ready to send to a friend — the four after it are optional, in descending order of certainty.

Phase 0 · Ongoing

Ground rules

Conventions that apply to every phase below, so they don't have to be repeated eleven times.

RuleDetail
Test locally before pushing non-negotiable Nothing goes to GitHub Pages to find out whether it works. Every change is run and checked on localhost first; the deploy is how it reaches your phone, not how you discover a bug. Pushing broken code to main also means the live app is broken for anyone else using it, and a service-worker mistake can leave them stuck on it. See Running it locally below.
Ship each phase Every phase ends on main, deployed to GitHub Pages, working on your phone — after it already worked locally. No long-lived branches, no half-landed refactors.
Bump the build, every deploy Every deploy that touches a precached file increments BUILD in sw.js. This is the cache buster: skip it and installed apps keep serving the old files forever. It is not tied to the version number and has no meaning beyond "this is newer than the last one".
Bump the version, every phase APP_VERSION in js/main.js is the footer stamp and tracks phases, not deploys: it reads 0.N once phase N is complete. Completing Phase 7 is what makes it 1.0. Most releases leave it alone.
Update the SW file list Splitting one JS file into fifteen means fifteen entries the service worker must precache. This is the single easiest thing to get wrong during the refactor — see the Phase 1 risk.
Migrate data forward, never sideways Every shape change ships a migration that runs on load and is safe to run twice. Old entries keep rendering. Nothing in a reader's finished list is ever lost to a schema change.
Enhancements degrade Search, availability, and AI each have an explicit off-state that leaves the app fully usable. Test each phase with the network disabled before calling it done.
Manual QA pass Same checklist each release, run locally first: cold start offline, sign in/out, add via search and manually, finish a book, set one down, switch vibe, two windows in sync. Takes five minutes; catches nearly everything.

Running it locally

The app can't be opened as a file:// path — ES modules, the service worker, and Firebase auth all need an origin. It does not need a build step or any dependencies; it needs a static server:

# from the repo root
python3 -m http.server 8000
→ http://localhost:8000

That's the whole dev environment. localhost counts as a secure context, so the service worker registers, the PWA installs, and Firebase auth works there exactly as it does in production — localhost is an authorised domain in Firebase by default (worth confirming once in the console rather than assuming).

SituationHow to handle it
Your changes don't appear Almost always the service worker serving its cache. In DevTools → Application → Service Workers, tick Update on reload and Bypass for network while developing. This is the single most common time-waster in this project, and it looks exactly like a bug in your code.
Testing sync between devices Two browser windows on localhost — one normal, one private — signed into the same account is enough for almost everything, since both talk to the same Firestore project.
Testing on a real phone A phone hitting http://<your-ip>:8000 gets no service worker, because that origin isn't secure — so offline and install behaviour can't be tested that way. Use USB port-forwarding (Chrome DevTools remote devices) or an HTTPS tunnel such as cloudflared, which does give a secure origin. Add the tunnel's hostname to Firebase's authorised domains if you need to sign in.
Anything destructive Local dev writes to the real Firestore project. For migrations, deletion, or club rules (Phase 11), use the Firebase emulator suite instead of your live data — Phase 11 needs the emulator regardless, for its rules tests.
Before you push Confirm the QA checklist passes locally, then deploy and verify the upgrade path from the previous build on a device that already has the app — a fresh install hides exactly the service-worker bugs that matter.
Phase 1 · Foundation

Refactor: modules & a real state store

Break app.js into focused modules and put a single state store underneath them. Zero user-visible change — if anyone notices this shipped, something went wrong. Everything after this phase is dramatically cheaper because of it.

Do this first No new features Unblocks 2–6

Why now

Today app.js is 476 lines holding DOM lookups, event wiring, business logic, rendering, and the cloud-sync bridge all at once, communicating with sync.js through four window.__* globals. It works — but adding vibes, search, availability, and AI on top of it means four more features tangled into the same file. Every hour spent here is repaid three times over in Phases 2–7.

Auto-update is already built — don't rebuild it. sw.js already calls skipWaiting() on install and clients.claim() on activate; index.html already registers with updateViaCache:'none', calls reg.update() on load and on every return to the foreground, and reloads exactly once on controllerchange (guarded against both the first-install claim and reload loops). That is the complete, correct mechanism. This phase only removes the redundant tap gesture and adds the mid-input guard — the moving parts stay as they are.
Components are built mount-agnostic. Phase 2 introduces routing, and a component that assumes it lives at a fixed spot on one long page is a component that gets rewritten then. So each one takes a mount point, renders into it, and tears itself down cleanly — costing nothing here and saving the rework next phase.

Structure

Native ES modules, no bundler, no build step — this deploys to GitHub Pages exactly as it does today.

/
  index.html          — markup + <script type="module" src="js/main.js">
  sw.js               — service worker (precache list grows)
  manifest.webmanifest
  firebase-config.js

  /js
    main.js           — boot: load state, mount components, register SW

    /state
      store.js        — the single source of truth + subscribe()
      migrate.js      — forward migrations, safe to re-run
      persist-local.js— localStorage adapter
      persist-cloud.js— Firestore adapter (was sync.js)
      auth.js         — Google sign-in, session state

    /components
      current-reads.js  — each takes a mount point; none assumes a page position
      tbr-pile.js
      finished-list.js
      libraries.js
      header.js
      /modals
        finish-modal.js
        book-modal.js
        library-modal.js

    /ui

      modal.js        — shared open/close/backdrop/focus behaviour

    components.css    — panels, cards, lists, buttons, chips

The store

One module owns the shelf. Components never mutate state directly and never read from localStorage; they call actions and re-render on notification.

store.getState()              — current shelf, read-only
store.subscribe(fn)           — called on every change
store.dispatch(action)        — the only way to change anything

Actions: addCurrent, editCurrent, reorderCurrent, finishCurrent,
         addToTbr, editTbr, removeTbr, removeFinished,
         addLibrary, editLibrary, removeLibrary,
         setVibe, applyRemote, loadLocal

Note the current-read actions are already plural-shaped. The UI still renders a single book in this phase — but writing setCurrent here would mean rewriting every call site in Phase 4 for no reason. The data model goes to an array now; the interface catches up later.

Persistence hangs off subscribe: every change writes to localStorage, and also to Firestore when signed in. That replaces the window.__applyRemoteState / __getLocalState / __setCloudMode / __loadLocal / __cloudSave globals with ordinary imports — the sync logic itself is already solid and gets moved, not rewritten.

Deliverables

  • File structure above, in place and working
  • store.js with actions, subscribe, and immutable reads
  • Migration current → currentReads[] — the stored shape becomes an array now, while the UI still renders only the first entry. Zero visible change; it means Phase 4 ships a component, not a data migration on top of a component
  • Persistence split into local and cloud adapters behind one interface
  • All four window.__* globals removed
  • Every panel a self-mounting component that takes a mount point, renders into it, and tears down cleanly
  • Delete the tap-to-check-for-updates gesture on the footer version. Auto-update already works without it (see below); the tap is vestigial, and a hidden gesture that duplicates automatic behaviour is just something else to maintain. The version stays visible as a plain label — it's the first thing worth knowing when something's wrong
  • Guard the auto-reload. The one real gap in the current mechanism: an update can reload the page while someone is typing in a modal. Hold the reload while a modal is open or an input has content, and apply it at the next quiet moment instead
  • Shared modal behaviour extracted once (open, close, backdrop, Escape, focus trap) instead of re-implemented per modal
  • styles.css split into tokens / base / components, with every colour promoted to a custom property — the groundwork Phase 3 depends on
  • sw.js precache list updated for every new file
  • Short ARCHITECTURE.md: where things live and how state flows

Acceptance criteria

  • Every existing feature behaves identically — set current, edit, finish with feeling and moods, TBR add/edit/remove, libraries, collapsible finished list
  • Existing saved data loads untouched, including legacy rating and notes entries
  • A shelf saved before this phase migrates to currentReads[] on load, renders identically, and survives a second load without duplicating the entry
  • Sign in on two devices; a change on one appears on the other
  • Sign out reverts to the local shelf; sign in re-attaches without duplicating or wiping
  • Cold start offline, from the home screen, works
  • A deployed change reaches an already-installed device on next foreground, with no interaction
  • The footer version is a plain label — tapping it does nothing
  • No reload happens while a modal is open or a field has text in it
  • No console errors on any path
  • Nothing looks or behaves differently. Screenshot the app before and after; the only difference should be the version number
Risk — the stale service worker. The precache list is now fifteen files instead of three. Miss one and it 404s offline; forget the cache-name bump and returning users are stuck on the old bundle with no way back short of reinstalling. Mitigation: bump CACHE as the first commit of the phase, not the last; test the upgrade path from a device already running v13 rather than from a fresh install, which hides exactly this bug.
Risk — a silent sync regression. The current sync code handles genuinely hard cases (multi-tab persistence, seeding only on server-confirmed empty, not blocking the UI on a slow handshake). Those behaviours are easy to lose while moving code. Mitigation: move sync.js as intact as possible — change its imports and its interface, not its logic — and re-test the first-login seed path with a fresh account before shipping.
On separating frontend and backend. This phase separates the frontend internally. The actual backend split lands in Phase 6, where the Cloudflare Worker appears — because that's the first thing that genuinely can't run in the browser. Firebase already plays the backend role for auth and data, and doesn't need replacing.
Phase 2 · Foundation

Navigation & the shell

Replace the single phone-length scroll with a tab bar and real routes, and move configuration behind the Hidden Shelf. The first change anyone will notice — and the frame every later phase mounts into.

Needs Phase 1 Shapes Phases 3–11 Small, but do it early

Why now, and not later

The single scroll worked with four panels and a short Finished list. It doesn't survive this plan: Current Reads, TBR, Coming Soon, Libraries, Clubs and an archive that grows forever leaves the daily-use surfaces buried under history. Doing this before the feature phases means Coming Soon (Phase 8) and Clubs (Phase 10) arrive into a structure that already has a place for them, rather than each one negotiating for space on a page that's already full. The design is Spec §04.

It's deliberately its own phase rather than part of the refactor. Phase 1 promises that nothing changes visibly, and that promise is worth keeping intact — it's what makes the refactor safe to ship and trivial to verify. This phase is where visible change is the whole point.

Structure

  /js
    /routes
      router.js       — hash routing, back-button behaviour, focus on change
      reading.js      — #/          current reads + TBR (+ coming soon later)
      finished.js     — #/finished  the archive, with room to be good

    /components
      tab-bar.js
      hidden-shelf.js   — "The Hidden Shelf": card, places, record
      libraries.js      — moved: now rendered inside the sheet

    /ui
      sheet.js          — the sheet's own open/close/focus behaviour

Hash routing, not the History API. Hash routes need no server rewrite rules, which keeps this deployable to GitHub Pages exactly as it is today. Phase 10 needs routing regardless, because a club invite has to be a link.

Deliverables

  • routes/router.js — #/ and #/finished to start, correct back-button behaviour, unknown routes falling back to Reading, and room for #/clubs and #/club/<code> later without rework
  • Tab bar — two tabs for now (Reading, Finished), fixed to the bottom on a phone with env(safe-area-inset-bottom) honoured, moving into the header as plain text links above the wide breakpoint. Built to take a third tab without a redesign
  • Reading route: Current Reads and the TBR pile — everything touched daily, nothing else
  • Finished route, and the things it could never afford at the bottom of a scroll: filterable by feeling and vibe, searchable by title or author, newest first, with a plain count. Filters are built over an open set of states — their chips are derived from the entries themselves — so Phase 4 can add "set down" without reworking them. Not grouped: vibes are multi-valued, so any grouping would file a book in two places at once, and genre isn't in the data model until Phase 4. No charts, no pace, no stats — a count is a memory, a graph is a target
  • Vibes that fit more than fantasy — three groups (Atmosphere, Story, Mind) plus a free-text "new vibe" whose entries are read back off the books carrying them, so horror, science fiction and non-fiction stop borrowing words meant for something else
  • Per-tab scroll position preserved within a session; cold start always lands on Reading, never on the last tab used
  • No badges, no counts, no dots on the tab bar — the rule written down before anything wants to break it
  • The Hidden Shelf behind the header bookmark: vibe, your card, libraries, and your record (export and delete), with the libraries list moved off the main screen into it
  • Favourite bookstores — the same saved-place list as libraries, sharing one implementation (places.js) rather than a second copy of it. Phase 5 grows real availability and buy links onto these
  • A "how I read" format preference was built here and removed: it stored a setting nothing read, and a control that does nothing is worse than the question going unasked. If Phase 5 wants to know which borrow and buy links to show, that's the phase that should ask
  • Sheet reuses the Phase 1 focus-trap helper rather than growing a second implementation
  • sw.js precache list updated for the new files

Acceptance criteria

  • Reading and Finished are separate places, and the daily screen no longer scrolls past an archive
  • The back button moves between tabs and never unexpectedly leaves the app
  • #/finished opens the Finished tab directly, from a cold start and from a pasted link
  • Switching tabs and returning preserves scroll position; quitting and reopening lands on Reading
  • Changing tabs moves focus to the new view's heading and is announced by a screen reader
  • The tab bar clears the iOS home indicator and never covers the last row of any list
  • Every library action still works, from inside the sheet
  • The finished list can be filtered to "everything I loved" and searched by author
  • On a wide screen there is no bottom bar, and the existing multi-column layout is intact
  • Fully keyboard-operable; the sheet traps focus and restores it on close
Risk — a cached shell serving new routes. A hash fragment never reaches the service worker, so #/finished is served by whatever is cached for the page — which after this phase may be a shell with no tab bar in it. Mitigation: the cache-name bump Phase 0 already requires covers it, but verify by opening #/finished on a device running the previous build rather than a fresh install.
Risk — the bar covering content. A fixed bottom bar eats the last row of every scrollable list, and on a notched phone it collides with the home indicator. Mitigation: env(safe-area-inset-bottom) plus bottom padding on every route, checked on a real device — the simulator is forgiving about exactly this.
Keep it to two tabs. The temptation is to build the three-tab bar now because Clubs is coming. Don't — a tab pointing at nothing is worse than a bar that grows. Phase 10 adds the third tab, and all this phase owes it is not making that hard.
Phase 3 · Feature

Vibes

Let a reader choose the look of their library, and change it whenever they like. Visual only — every label stays put. The first phase where the refactor pays off.

Highest delight per hour Needs Phase 1 No backend

How it works

Every vibe is one CSS file setting the same fixed set of custom properties under a [data-vibe="…"] selector. Components reference tokens only and never know which vibe is active, so adding a sixth vibe is one new file plus one registry line.

/styles/vibes/
   otherworld.css   celestial.css   dark-academia.css
   cottage.css      seaglass.css

Each defines the same contract:
[data-vibe="cottage"]{
  --bg-1 --bg-2 --bg-texture
  --surface --surface-raised --line
  --ink --muted
  --accent --accent-2
  --font-display --font-body
  --radius --shadow
}

Deliverables

  • Five vibes: Otherworld (default), Cottage, Celestial, Dark Academia, Seaglass
  • Vibe registry module — id, display name, preview swatches, fonts to load
  • First-run picker: full-screen grid of cards, each a live miniature of the real UI in that vibe
  • Vibe control in the header, opening the same picker for changes
  • Inline head script that stamps data-vibe before first paint — no flash of the wrong theme
  • theme-color meta updated on switch so the installed PWA's status bar matches
  • Vibe stored locally for instant offline application, mirrored to the cloud profile for new devices
  • Per-vibe font loading — a vibe's webfont is only fetched when that vibe is active
  • Contrast audit results recorded per vibe

Acceptance criteria

  • A brand-new reader picks a vibe before seeing the shelf; an existing reader is never prompted and stays on Otherworld
  • Switching vibes re-skins in place — scroll position, open panels, and half-typed forms all survive
  • Reload in any vibe shows zero flash of the previous or default theme
  • Sign in on a second device and the vibe follows you
  • Every vibe passes WCAG AA on body text, buttons, chips, and links
  • Every vibe is legible in sunlight on a phone and doesn't glare in a dark room
  • prefers-reduced-motion disables the transition
Risk — hard-coded colours in components. Any literal hex left in components.css will look wrong in four of the five vibes, and they're easy to miss because the default vibe hides them. Mitigation: after the token split, grep for # and rgba( outside tokens.css and the vibe files. Every hit is a bug.
Phase 4 · Feature

Book search & autofill

Replace hand-typed titles with a search field that suggests real books — bringing correct spelling, covers, publication years, and the stable identifiers that Phases 4 and 5 both depend on.

Enables Phase 5 & 6 No key required Data model change

The source

Open Library's search endpoint. Verified working directly from a browser: no key, no registration, permissive cross-origin headers, and a single request returns everything needed.

GET https://openlibrary.org/search.json
      ?q=<query>
      &limit=6
      &fields=key,title,author_name,first_publish_year,cover_i,edition_count

→ { docs: [ { key: "/works/OL20893680W",
              title: "Piranesi",
              author_name: ["Susanna Clarke"],
              first_publish_year: 2020,
              cover_i: 10226290 } ] }

Covers: https://covers.openlibrary.org/b/id/<cover_i>-M.jpg

Deliverables

  • services/books.js — search, debounce, request supersession, timeout, normalise to the app's Book shape
  • Typeahead component: cover thumbnail, title, author, year; arrow-key navigation; proper listbox semantics
  • Search-first add flow on both the TBR pile and the Current Reads panel
  • Current Reads becomes a list. The panel gains its own + Add control using the same typeahead, holds up to three books, renders the first large and the rest as compact rows, and supports drag-to-reorder. Each entry keeps its own Edit and Finish. At three, adding suggests finishing or shelving one rather than refusing outright. The data migration for this already landed in Phase 1 — this is UI only
  • Optional format chip on a current read — print / ebook / audio — never prompted for, purely so three simultaneous books are distinguishable at a glance
  • Set it down (DNF). A third action beside Edit and Finish, opening the same modal with two outcomes: not right now (returns to the TBR pile, changes nothing else) and not for me (goes to the record marked as set down, and is excluded from future suggestions). Feeling and moods stay optional on both
  • Set-down entries render in the Finished list with a distinct marker and are covered by the filters built in Phase 2
  • Series capture — seriesKey, seriesName and seriesPosition stored from the search result when Open Library provides them, absent when it doesn't. Nothing in this phase uses them; Phases 6 and 8 do
  • Permanent "add manually" escape hatch below every result list
  • Duplicate detection against TBR and Finished, with a jump-to-existing action
  • Book model extended with workKey, coverId, year, source; migration leaves existing books untouched and fully functional
  • Cover art returns to the Current Reads panel and list rows — only where a cover exists, never a placeholder
  • Cover images lazy-loaded, with the service worker caching them for offline viewing

Acceptance criteria

  • Typing three characters surfaces relevant results within a second on a normal connection
  • Picking a result adds the book fully populated, in one tap
  • Manual entry still works and is never more than one tap away
  • Offline, the search field degrades to manual entry with a clear note — adding never blocks
  • Rapid typing never leaves a stale result list on screen
  • Existing hand-entered books keep working, with no cover and no errors
  • Three books can be current at once; finishing one leaves the other two exactly as they were
  • A book set down as not right now is back on the TBR pile and still suggestible; one set down as not for me is in the record and never suggested again
  • Books whose series is unknown behave exactly as before — no empty series labels anywhere
  • Reordering changes which book renders as the headline, and survives a reload and a device switch
  • A reader with one current book sees no difference from before the phase
  • Fully keyboard-operable and announced correctly by a screen reader — including reordering, which must have a keyboard path and not be drag-only
Risk — search quality on short queries. Open Library relevance can be uneven; typing "the" returns noise. Mitigation: require three characters, sort by edition_count so the well-known edition wins, and cap at six results. If quality still disappoints, the fallback is Google Books as a second source — but it needs a key, so try ranking tweaks first.
Phase 5 · Feature

Libraries, Libby & local shops

Turn the Libraries panel from a list of bookmarks into something that answers "can I get this right now?" — with real availability from a real library, and a link that lands on the right title in Libby.

The ethos, made real Needs Phase 4 Undocumented API

The endpoints

OverDrive's public catalogue API — the one Libby's own web app uses. Verified live: it permits cross-origin browser requests and returns exactly the availability data this needs.

Find a library system
GET https://thunder.api.overdrive.com/v2/libraries?query=<place or name>
    → items[].preferredKey, .name, .links.libraryHome

Check a title's availability at that library
GET https://thunder.api.overdrive.com/v2/libraries/<key>/media?query=<title>
    → items[]: isAvailable, availableCopies, ownedCopies,
                  holdsCount, estimatedWaitDays, type.id (ebook|audiobook), id

Deep links (plain URLs — these cannot break)
https://libbyapp.com/search/<key>/search/query-<title>/page-1   search
https://share.libbyapp.com/title/<id>                          a specific title

Deliverables

  • services/libby.js — library lookup, availability check, deep-link builders, timeouts, and a hard feature-flag to disable availability wholesale
  • Add-library flow: search real library systems by name or place, pick one, store its key
  • Name your own library. After picking, a What do you call it? field pre-filled with the official name and freely editable — "Mom's card", "County", "the good one". That label is what the app shows everywhere; the official name is kept underneath and only surfaces to disambiguate two similar entries. Renaming never touches the stored key
  • Library entries typed as library, bookshop, or bookmark; all three named the same way; only libraries get availability
  • Multiple libraries, reorderable, first one primary for availability
  • Borrow row on each TBR book: available now / estimated wait / not in collection / not set — using the reader's own name for the library
  • Availability results cached in memory for the session so scrolling the TBR doesn't re-query per book
  • Bookshop.org fallback link where a purchase makes sense; no Amazon links anywhere
  • Plain "Search this on Libby" link always present, independent of any availability lookup

Acceptance criteria

  • A reader can find their real library by typing their city, name it whatever they want, and see that name everywhere afterwards
  • A book their library holds shows accurate copies, holds, and estimated wait
  • Tapping through lands on that book in Libby, ready to borrow or hold
  • With availability disabled by flag, every borrow row disappears cleanly and the Libby search link still works
  • With the endpoint failing or timing out, the row simply doesn't render — no error, no spinner, no broken layout
  • With no library configured, the TBR shows a single quiet prompt, not a warning per book
  • Two libraries with similar official names are still distinguishable by the reader's own labels
Risk — the API is undocumented and unsupported. It works today; it has no compatibility promise and could change shape or start blocking browser origins at any time. Mitigation: build it as a strictly optional enhancement behind a single flag from day one. The deep links are ordinary URLs and cannot break, so the core promise — "take me to Libby for this book" — survives the enhancement's failure completely. Ship the deep links first and the availability layer second, so there's always a working state to fall back to.
Risk — title matching. Matching a book from Open Library to the same book in OverDrive is done by title-and-author text, which will occasionally match the wrong edition or miss entirely. Mitigation: prefer ISBN matching where Phase 4 captured one; show the matched title in the row so a wrong match is visible rather than silent; treat "not found" and "not owned" as the same neutral state rather than asserting the library doesn't have it.
Phase 6 · Backend + Feature

Backend + AI recommendations

Stand up the one piece of real backend the app needs — a serverless function holding the API key — and use it for the headline feature: describe a mood, get books back, triage them in one tap.

The headline feature Needs Phase 4 Costs real money

Architecture

Browser (GitHub Pages)          Cloudflare Worker              Anthropic API
─────────────────────           ─────────────────              ─────────────
 POST /recommend        ──▶     verify Firebase ID token
 Authorization: <token>         check + increment daily quota
 { moods, freeText,             build prompt
   tasteSummary,                call model               ──▶   claude-opus-5
   exclude[] }                  return structured JSON   ◀──   (structured output)
                        ◀──     { suggestions[], remaining }

 verify each title against Open Library, drop anything that doesn't resolve
 render cards → + TBR / Already read / Pass

The Worker is the entire backend: one file, one route, free tier, deployed independently of the site. The API key lives in a Worker secret and never reaches a browser.

Deliverables — backend

  • /api directory in the repo: Worker source, wrangler.toml, and a README covering deploy and secret rotation
  • Firebase ID token verification; the user ID is derived from the verified token, never from the request body
  • Per-user daily quota in Workers KV, returning remaining count on every response
  • CORS locked to the Pages origin
  • Structured output so responses are always valid {title, author, why} objects
  • Typed error responses the UI can show verbatim: unauthenticated, over quota, upstream failure
  • No logging of prompts, titles, or results — only a per-user counter

Deliverables — frontend

  • "Find me something…" entry point on the TBR panel
  • Request sheet: mood chips (the same vocabulary as the finish form) plus a free-text field, with the remaining daily count shown before you ask
  • Taste summary builder — recent loved books and most-used moods, compressed; the full shelf never leaves the device
  • Exclusion list assembled from TBR, Finished, books set down as not for me, and previously passed suggestions
  • Abandoned-series suppression — a series whose earliest-read entry was marked not for me or set down that way is excluded whole, so book two of something you bounced off is never offered. Uses the seriesKey captured in Phase 4; where series data is missing the rule simply doesn't apply
  • Verification pass against Open Library; unresolvable suggestions dropped silently
  • Suggestion cards with the model's reason, and three one-tap actions: + TBR, Already read, Pass
  • Passed titles persisted so a second ask returns genuinely different books
  • Errors shown as one plain sentence and a Retry, inside the sheet

Acceptance criteria

  • Asking for a mood returns five real, existing books in a few seconds
  • Nothing already on the shelf or previously passed is ever suggested
  • No book from a series whose first read was not for me is ever suggested
  • The taste summary — recent loved titles, frequent moods, exclusions — is confirmed good enough in practice before anyone considers sending the full finished list. Judged on results, not assumed
  • Each suggestion explains itself in a way that references the reader's actual taste
  • Every action lands the book in the right place in one tap
  • Asking twice in a row returns a materially different list
  • Signed out, the feature is hidden entirely — not shown-then-rejected
  • Calling the Worker without a valid token fails; calling with someone else's user ID in the body changes nothing
  • Over quota produces a clear message, not an error
  • The rest of the app is completely unaffected by any AI failure
Budget check before building. At roughly 1.5k tokens in and 800 out, Opus 5 costs about 2¢ per recommendation. A reader using the full 10/day allowance costs ~$7/month. That's fine for you and a few friends and does not survive contact with strangers. Two levers, both one line in the Worker: lower the daily cap, or switch to Haiku 4.5 at roughly a quarter of the cost. Set a billing alert on the Anthropic account before the first real user touches this.
Risk — invented books. A recommender that confidently suggests a book that doesn't exist destroys trust in the whole feature. Mitigation: the Open Library verification pass is not optional — it's the acceptance criterion. Anything unverifiable is dropped before it's rendered, and a short list of real books beats five with one fake.
Risk — quota storage limits. Workers KV's free tier allows ~1,000 writes/day, and each recommendation is a write. Fine for a handful of readers; a wall if this ever grows. Mitigation: one counter write per call keeps it linear and predictable — watch the number, and move to a Durable Object if it ever gets close.
Phase 7 · Polish

Ready to share

The gap between "works for me" and "I can send this to a friend without explaining anything."

Needs 1–6 Low risk

Deliverables

  • First-run flow that reads as a welcome rather than a form: vibe picker → sign in (or "just use it on this device") → add your first book
  • Empty states that teach — each panel explains what it's for and offers the action that fills it
  • Export the whole shelf to JSON; delete everything, with confirmation
  • Import a previously exported shelf, merging rather than replacing
  • Accessibility pass across every vibe: focus order, focus rings, live regions, reduced motion
  • Performance pass against the budgets in the spec, measured on a real mid-range phone
  • README rewritten for someone who isn't you
  • Genuine error states for the paths that currently alert()

Acceptance criteria

  • A non-technical friend installs it, picks a vibe, signs in, and adds a book without being told how
  • Every panel is understandable when empty
  • A shelf can be exported, wiped, and re-imported intact
  • No alert() remains anywhere in the app
  • Lighthouse: accessibility and PWA both green, in every vibe
Phase 8 · Feature

Coming soon

Tell a reader that an author they love has a book on the way — months before they'd otherwise find out, and with a library hold or an independent preorder one tap away.

Needs Phase 4 Highest delight per line of code Unverified data sources
Do the feasibility spike first — this phase is not approved until it passes. The Open Library search and the OverDrive availability endpoints were both verified against live data before their phases were written. Nothing in this one has been. Before building anything, spend an hour querying Google Books and Open Library for forthcoming titles by five real authors with books known to be coming. If fewer than three of five turn up with a usable date, stop and ship only the author-announced path in Phase 10 — which is a better source anyway. A Coming Soon panel that misses the book you were waiting for is worse than no panel.

The sources

Forthcoming titles by an author (primary — has future publishedDate)
GET https://www.googleapis.com/books/v1/volumes?q=inauthor:<name>&orderBy=newest
    → items[].volumeInfo: title, publishedDate, industryIdentifiers, imageLinks
    → filter to publishedDate > today

Author identity + known works (the "is this new to me?" anchor)
GET https://openlibrary.org/search/authors.json?q=<name>
GET https://openlibrary.org/authors/<key>/works.json

On order at the reader's own library (best answer — library first)
GET https://thunder.api.overdrive.com/v2/libraries/<key>/media?query=<title>
    → pre-release titles carry an expected availability date

Announced by the author (Phase 10 — highest confidence, covers indie)
Firestore: releases/{authorKey}/…

Deliverables

  • services/releases.js — author resolution, forthcoming-title lookup across sources, de-duplication, date-precision handling, timeouts, and a hard feature flag to disable the whole panel
  • Watch control on any author name in Finished, TBR, or Current Reads; watches stored on the reader's own document
  • Opt-in prompt in the finish modal when a book is marked 💛 Loved — offered once per author, never repeated
  • Coming Soon panel on the Reading tab, rendering only when there is something to show; sorted by date, nearest first. It sits below the TBR pile and does not get its own tab — if it ever grows big enough to want one, that's a signal it's competing with the books being read
  • Per-entry actions: + TBR, place a hold where the library lists it, preorder via Bookshop.org or a shop the reader added
  • Confidence labelling — a date from a catalogue and a date from an author look different on screen
  • Date precision respected: "March 2027" when that's all that's known, never a fabricated day
  • False-positive suppression: re-issues, box sets, translations and audiobook re-releases matching a work already on the shelf are dropped
  • Next in series — the highest-value case of this whole phase. A forthcoming book sharing a seriesKey with something the reader loved is surfaced with that connection stated ("book 3 of Piranesi's series"), not as an anonymous new title
  • Abandoned series never surface — the same rule as the recommender: a series whose first read was not for me is suppressed here too. Being told a sequel is coming to a book you gave up on is worse than being told nothing
  • Daily per-author check limit, staggered across authors, cached with the entry — thirty watches must not mean thirty requests on a cold start
  • Entries expire on release day: added to TBR if the reader asked, silently removed otherwise
  • Watch management in Settings — see everyone you watch, unwatch in one tap

Deliverables — deferred to a follow-up, deliberately

  • Push notification on release day. Opt-in per reader, and on iOS only possible for a home-screen-installed PWA. An app with no streaks and no badges does not earn the right to push until the panel itself has proven useful
  • Nightly server-side sweep in the Worker. Only worth it if client-side checking proves too slow or too spammy — it is not needed for the feature to work

Acceptance criteria

  • Watching an author with a known forthcoming book surfaces it, with a correct date, within one app open
  • Watching an author with nothing coming produces no panel and no empty state
  • No book already on the reader's shelf ever appears as "coming soon"
  • A sequel to a loved book is surfaced with the series connection visible
  • No book from a series the reader abandoned ever appears
  • A re-issue of a book the reader has finished does not appear
  • Thirty watched authors do not produce a visible delay or a request storm on a cold start
  • With every source failing or offline, the panel does not render — no error, no spinner, no broken layout
  • With the feature flag off, every trace of watching and Coming Soon disappears cleanly
  • Unwatching an author removes their entries immediately
Risk — the data simply isn't there. This is the likeliest failure in the whole plan, and unlike the OverDrive risk it can't be mitigated by a fallback link. Mitigation: the spike above, run before any code. If coverage is thin, the feature narrows to author-announced releases rather than shipping something that quietly misses half of what it promises.
Risk — wrong author, same name. Author names are not unique, and matching by name will eventually attach a stranger's book to a watched author. Mitigation: resolve to an Open Library author key at watch time and match on that key, never on the name string. Where only a name match is possible, show the entry with the matched author's name visible so a wrong match is obvious rather than silent.
Risk — dates that move. Publication dates slip constantly, and a wrong date erodes trust in the panel faster than a missing entry does. Mitigation: show precision honestly, update silently when a source changes, and never promise a day the source didn't give.
Phase 9 · Sustainability

Keeping it running

Make the running cost visible, bounded, and — if anyone feels like it — coverable. Small, boring, and the difference between a project that survives a bill and one that quietly gets switched off.

A day's work Needs Phase 6 for the caps Do before wide sharing

Full reasoning, cost figures and the options that were rejected are in Spec §15. This phase implements the four that were accepted, cheapest first.

Deliverables — spending less

  • Monthly budget ceiling in the Worker. When the month's AI spend passes a configured figure, the recommender returns a typed budget_exhausted response and the UI says so in one plain sentence — "the recommender is resting until the 1st". The rest of the app is untouched. A known limit beats a surprise invoice
  • Per-user daily cap made configurable rather than hard-coded, so lowering it from 10 to 5 is a config change
  • Model choice as a Worker config value, so the Haiku 4.5 swap — roughly a fifth the cost — is one line and one deploy
  • Billing alert on the Anthropic account, set before anyone who isn't you touches the feature. This is not optional and it is not code — do it first
  • Rough spend visible to you: the Worker's existing per-user counter extended with a monthly total, readable without adding any logging of prompts, titles or results

Deliverables — bringing some in

  • Bring your own key. A reader can paste their own Anthropic API key in Settings; when present, their requests use it and bypass the shared cap entirely. Stored on their own device only — never synced to Firestore, never sent anywhere but the Worker, clearable in one tap. Costs nothing and removes the ceiling for the technical few
  • A quiet donation link in Settings — Ko-fi or GitHub Sponsors, both of which take no platform cut from an individual. One line of text, no modal, no badge, no counter, no reminder, nothing in the reading flow
  • Bookshop.org affiliate on the purchase links that already exist, with the disclosure shipping in the same release as the tag — at the point of the link, in plain language, not in a policy page. Spec §09 promised this; breaking it for revenue would cost more than the revenue is worth
  • A short, honest About & costs page: what the app costs to run, what it earns, and where the money goes. Two paragraphs

Acceptance criteria

  • With the monthly ceiling reached, the AI feature explains itself in one sentence and everything else works normally
  • Lowering the daily cap or switching the model requires a config change and a deploy, not a code edit
  • A reader's own API key works, never leaves their device except to the Worker, and can be removed
  • Every affiliate link is disclosed where it appears — verified by looking at each one, not by trusting the implementation
  • No analytics, no ad network, no third-party script has been added anywhere
  • The donation link is impossible to encounter unless you go looking in Settings
Risk — the disclosure quietly not shipping. Affiliate tags are trivial to add and the disclosure is easy to leave for later, at which point the app is doing something Spec §09 and §13 both say it doesn't. Mitigation: treat them as one deliverable, not two. If the disclosure isn't written, the tag doesn't go in.
Risk — a stored API key. A reader's own key in localStorage is a real credential on a shared device. Mitigation: local-only and never synced (a synced key is a key in someone else's database), an obvious clear action, and plain text at the input explaining exactly where the key goes and that it is stored on this device alone.
Phase 10 · Feature

Authors

Let a verified author announce their own forthcoming books to readers who already chose to watch them — and host a read-along for one. The second role, on the same account.

Needs Phase 8 Club hosting deferred to Phase 11 Verification is the whole feature

Design and the deliberately long list of things an author cannot do are in Spec §12. The short version: an author is a reader with one verified flag, reaching only readers who opted in, learning nothing about who they are, and never able to pay for anything.

Why this is worth building last and not first. It is the fix for Phase 8's weakest link — the one entity that reliably knows a book is coming is the person writing it, and for indie and small-press books it's the only source. But it's worth nothing until there are readers watching authors, which is Phase 8's job.

Data model

authors/{authorKey}
  name, uid, verifiedAt, verificationMethod, links[]
  (no watcher count — deliberately not built yet, see below)

  releases/{releaseId}
    title, releaseDate, datePrecision, isbn, coverUrl,
    preorderUrl, libraryNote, announcedAt

Rules: world-readable (an announcement is public by nature).
       Writable only by the uid that verified against this authorKey.
       Nothing here ever records who is watching.

Deliverables

  • Claim flow in Settings — search for your own author entry, then verify
  • Domain verification: sign in with an email at the author's own domain, or place a token file at a URL on their site. Fully automatic, and the only method that scales
  • Manual review path for everyone else: a claim queue only you can see, approved against a public author page
  • Announcement composer: title, release date with explicit precision, cover, preorder link, optional library note. Editable and retractable
  • Announcements surfaced in the Coming Soon panel of watching readers only, visibly labelled as author-announced and rendered no larger and no higher than a catalogue entry
  • Author metadata corrections, scoped to that author's own books and visible only inside this app
  • Author search in the club and watch surfaces, showing the verified badge; readers remain unsearchable
  • Reader-side off switch that hides authors, watches and Coming Soon entirely
  • Revocation: an author role can be removed, taking their announcements with it

Deliberately not in this phase

  • The watcher count. An author was going to see how many readers watch them, withheld below a threshold. It isn't built. It is the only metric in an app that has none, and nobody has yet asked for it — so it waits for an author to say they need it, and for a reason that isn't "because other platforms have one". Nothing in the data model depends on it, and adding it later costs an aggregate query. If it does arrive: aggregate only, never names, and withheld below a threshold so a small following can't be deduced from who was invited
  • Author-hosted clubs — they need clubs, which is now Phase 11. Ships there, not here

Acceptance criteria

  • An unverified claim stores nothing, shows nothing, and grants nothing
  • A verified author's announcement reaches watching readers and no one else — verified by checking a non-watching account sees nothing
  • An author can obtain no information about any individual reader through any surface in the app
  • An author sees no reader count of any kind — there is no number to find in this build
  • An author cannot write to any author key but their own — verified against the rules, not the UI
  • An author-announced date is visually distinguishable from a catalogue date
  • Nothing about authorship reaches the AI recommender's prompt
  • With the reader-side switch off, the app is identical to Phase 9
  • Revoking a role removes the announcements with it
Risk — impersonation. An unverified author claim converts Phase 8's most trusted source into an attack on readers. Mitigation: nothing displays before verification, ever. There is no "pending" badge, because a pending badge is a badge.
Risk — manual review doesn't scale. It is fine at this size and it is the first thing to break if the app grows. Mitigation: named as a known limit in Spec §12 with two honest exits — close claiming to domain-verified authors, or pause new claims. Never lower the bar to keep up with volume.
Risk — this becomes a marketing channel. Every feature request after launch will push toward broadcast, promotion and paid reach, and each one individually will sound reasonable. Mitigation: the "cannot do" table in Spec §12 is the spec, not a starting position. Watching is the entire permission model; if that ever stops being true, the feature has become the thing this app was built not to be.
Phase 11 · The big one

Reading together

Book clubs: a small group, one shared book, and a conversation that structurally cannot spoil it. The first genuinely multi-user feature in the app.

The biggest departure Needs 2 & 4 Security rules are the feature Largest maintenance surface
Read this before starting. Every phase before this one is a single-player app with a sync backend: the worst bug loses one person's data, and the security model is four lines. A club is shared state — other people's writes, other people's words, and a rule set where a mistake shows a stranger something private. It is also the only feature here with a moderation surface, however small. Spec §10 is unusually blunt about this on purpose. It is entirely reasonable to stop before this one and never build it.

Data model

clubs/{clubId}
  name, book{}, ownerUid, joinCode, visibility, createdAt
  checkpoints[]            — [{ id, label, dueAt? }], may be empty
  memberUids[]             — denormalised, for the rules to read cheaply

  members/{uid}
    displayName, joinedAt, progress, finishedAt, feeling, moods[]

  messages/{msgId}
    uid, text, checkpointIndex, createdAt, deletedAt?

users/{uid}
  clubIds[]                — so a reader can list their clubs without a query
  blockedUids[]            — per-reader, applies everywhere

The spoiler gate lives in the rules, not the UI. A member may read a message only when message.checkpointIndex <= their own members/{uid}.progress. Hidden-in-the-UI is not hidden — anyone can open a console. This single rule is the feature; if it can't be expressed and tested, the design changes rather than the promise.

Deliverables

  • Firestore rules for clubs, members and messages — membership-gated reads, the checkpoint gate above, owner-only club mutation, author-only message edit and delete
  • A rules test suite run against the Firestore emulator, asserting the negative cases: a non-member reads nothing; a member at checkpoint 2 cannot read a checkpoint 5 message; a member cannot raise another member's progress; a non-owner cannot remove a member or change the book
  • Clubs tab — the third tab appears in the bar built in Phase 2, and disappears again cleanly when the feature flag is off. Routes #/clubs and #/club/<code>, the latter doubling as the invite link
  • Author-hosted clubs — deferred here from Phase 10: a verified author can create a club for one of their own books, with no special powers inside the thread. Falls away cleanly if Phase 10 was skipped
  • Create a club from any TBR or current-read book; invite link with a join code
  • Join flow: preview the book and member count, one button, and the book lands on the joiner's Current Reads — or their TBR if they're already at three
  • Checkpoints: owner-defined, optional labels and dates; a club with none has one implicit finished checkpoint
  • Progress control — tap the checkpoint you've reached; the only progress data in the app
  • One flat message thread per club, each message pinned to its author's checkpoint, gated on read
  • Finish-in-club wired to the existing finish modal — one action finishes the book in both places, and reveals feelings both ways at that moment
  • Member list showing name and checkpoint only
  • Leave, and leave and delete my messages, as two distinct actions
  • Owner tools: remove a member, change the book, delete the club
  • Per-reader block, applying across every club, needing no one's permission
  • Club directory: listed clubs findable by the book they're reading. Readers remain unsearchable — this indexes clubs, not people
  • Offline: club content readable from cache, posting queued until reconnect, never blocking the shelf
  • Account deletion extended to remove the reader from every club and delete their messages

Acceptance criteria

  • Two real accounts on two devices can create a club, join, post, and see each other's messages
  • A member at an early checkpoint cannot see a later message — verified in the console, not the UI
  • Feelings stay invisible until the reader has finished, then appear for everyone at once
  • Nothing outside the club's book is ever readable by another member — verified by trying
  • Leaving removes access immediately, and the delete-my-messages option actually deletes them
  • A blocked member's messages are invisible in every club, permanently
  • The rules test suite passes, and every negative case genuinely fails when the rule is removed
  • Signed out, no club surface is reachable at all
  • A club with twelve members and several hundred messages stays inside the Firestore free tier
  • With clubs disabled by flag, the app is exactly what it was in Phase 10
Risk — a rules mistake leaks something private. The highest-severity risk in this plan. Every other failure mode degrades a feature; this one breaks a promise. Mitigation: the emulator test suite is a deliverable, not a nice-to-have, and it asserts denials rather than successes. Write the negative tests before the rules. Ship behind a flag and test with two real accounts before the flag comes off.
Risk — write volume. Clubs are the first feature that meaningfully multiplies Firestore writes: every message, every progress tap, every member document. Mitigation: progress is one integer on one document, messages are append-only with no counters to update, and the member list is denormalised so reading a club is one query. Watch the free-tier numbers after the first real club.
Risk — someone is unpleasant. Small and invite-shaped makes this unlikely, not impossible, and there is no moderation team. Mitigation: owner removal and per-reader block both ship in this phase, not later. The honest limit is documented in Spec §10 rather than hidden — and it's the reason readers stay unsearchable and listing is opt-in.
Risk — the owner disappears. Unresolved in the spec, and it will happen. Mitigation: decide before building, not after. Leaning toward automatic transfer to the longest-standing member after a long inactivity window, since a club that can never be dissolved is worse than one with a slightly arbitrary owner.

If you want to…Do this
Fix the thing that annoys you daily1 → 2. A Finished list that isn't buried under everything else, and a reading screen that's only the books you're reading.
See something delightful fastest1 → 3. Vibes are the highest delight per hour of work in the whole plan, and they prove the refactor was worth it. Phase 2 isn't a prerequisite, but doing it first means only styling the layout once.
Make daily use better fastest1 → 4. Never mistyping a title again is the change you'll feel every single time you add a book — and it's where reading three books at once arrives.
Build the thing that makes this different1 → 4 → 5. Library-first borrowing is the part no other reading tracker does honestly.
Get to the headline feature1 → 4 → 6. Phase 5 is not a prerequisite for AI; they're siblings, and either order works.
Get the best moment-of-delight after launch4 → 8. "Susanna Clarke has a book coming in March" is the single nicest thing this app could tell someone — if the data spike passes.
Sleep well before sharing widely9, on its own. It's a day, it needs almost nothing, and it's the difference between a surprise bill and a known ceiling. Do it before Phase 7's friends arrive, not after.
Build the ambitious one1 → 2 → 4 → 11. Clubs are the biggest change in the plan and the only one that makes this app something other people participate in — and the one that needs an audience before it makes sense, which is why it is now last. Also the one most reasonable to skip entirely.

Phases 5 and 6 are independent of each other — both only need 4. Do whichever you're more excited about; excitement is the scarcest resource in a personal project.

Phase 2 is cheap and everything visual after it inherits its frame, so it's worth doing before the feature phases even though only 8 and 11 strictly depend on it. The exception is if vibes are what will keep you interested — in that case do 3 first and accept restyling the tab bar afterwards.

After Phase 7 the ordering is genuinely yours. 9 is nearly free and should come early. 8 is the most delight per line of code, gated on a one-hour spike. 10 is worth little until 8 exists, and 11 is the most work and by far the most risk. Stopping at 9 is a complete, coherent product — 10 and 11 turn a personal shelf into something with other people in it, which is a different kind of commitment, not just a larger one. Clubs sit last because they need an audience to be worth anything: a book club with nobody in it is just a worse version of the shelf you already have.
